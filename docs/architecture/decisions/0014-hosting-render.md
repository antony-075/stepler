# ADR 0014 — Hosting: Render (staging first)

Status: Accepted for staging (2026-09-30); production to be confirmed when it is set up
Date: 2026-09-30

## Context

Stepler needs EU hosting for the web app (Next.js), the API (NestJS) and PostgreSQL 18 (the schema uses `uuidv7()`). Rule 17 prefers managed services. The branch model (docs/development/README.md) is: `dev` is local only, `stage` is deployed to staging with its own secrets, and `main` is production.

## Decision

- **Render, Frankfurt region.** It is described as code in `render.yaml` (a Blueprint), deploys the `stage` branch, and only deploys after CI passes (`autoDeployTrigger: checksPass`).
- **Web** is a public Docker web service (`0.5c-512mb`) with a `/healthz` health check.
- **API** is a private service (`pserv`, `0.5c-512mb`). It is reachable only by the web service over Render's private network (`API_INTERNAL_HOSTPORT` from `fromService … hostport`). The same-origin topology (spec §2) is unchanged.
- **PostgreSQL 18** is managed by Render (`0.1c-256mb`, 1 GB) with no public access (`ipAllowList: []`).
- **Migrations:** `preDeployCommand: node_modules/.bin/prisma migrate deploy` runs from the new API image before it serves. The API image therefore ships the Prisma CLI and `prisma/` (the CLI is a runtime dependency). `verify-images.sh` checks that the command applies migrations and is idempotent.
- **Client IP:** with `CLIENT_IP_HEADER=cf-connecting-ip`, the web server forwards only the IP from Cloudflare's `CF-Connecting-IP`, validated as one IP address, as a single `X-Forwarded-For`; it drops every other forwarding header. Cloudflare, in front of every Render service, sets that header from the connection it received and overwrites client-sent values. The API trusts one proxy (`API_TRUST_PROXY=1`). The spoofing check on staging is runbook step 7.
- **Other providers for staging:**
  - Cloudflare R2 bucket in the EU jurisdiction (ADR 0008);
  - Cloudflare Turnstile widget for the staging host;
  - Brevo SMTP for sign-in email (EU);
  - a separate Google OAuth client.
- **Domain:** the Render subdomain for now (`https://<web service>.onrender.com`); a custom domain comes later.
- **Secrets** are entered in the Render dashboard (`sync: false`). `APP_SECRET` is generated by Render. None are in the repository.

## Alternatives considered

- Fly.io: cheaper machines, more hands-on setup (fly.toml, Postgres operations).
- Railway: EU region, but usage-based billing is less predictable.
- Scaleway: EU company and the simplest GDPR story, but the most setup for this stack.
- Hetzner + Coolify: cheapest, but we operate the server ourselves.

## Consequences

- Staging costs about the two smallest instances plus the smallest Postgres (roughly $20–25/month in September 2026, before bandwidth). Paid instances are required for `preDeployCommand` and private services.
- The API image is larger because it contains the Prisma CLI and its engines.
- Per-IP limits stay in memory and are correct only with a single API instance; shared storage is still open (spec §21).
- Production needs its own services, database, bucket and credentials. It is a separate Blueprint or environment with branch `main`, decided when production is set up.

## Staging finding: X-Forwarded-For is forgeable on Render (2026-09-30)

The first design trusted the first `X-Forwarded-For` entry, based on Render guidance that it is the real client IP. The runbook check disproved this. With the preview limit set to 3, five requests carrying different forged `X-Forwarded-For` values all got 400 and never reached 429. Five plain requests from the same machine hit 429 on the fourth. Render keeps the client-sent value in front of the entries its proxies append.

The fix is `CLIENT_IP_HEADER=cf-connecting-ip`, as described above. The same spoofing check is repeated after deploy.

## Staging verified (2026-09-30)

On `https://stepler-staging.onrender.com`, after the `CF-Connecting-IP` fix (#14, deployed via #15):

- **Health:** `/healthz`, `/api/v1/health/live` and `/api/v1/health/ready` return ok; readiness reaches the database and the R2 bucket.
- **Pre-deploy migrations:** they ran without the OpenSSL warning.
- **Sign-in:** the owner signed in by magic link (mail through Brevo) and with Google.
- **Production hardening:**
  - `/api/docs` returns 404;
  - unsafe requests without `Origin` or with a foreign one get 403 `CSRF_ORIGIN_MISMATCH`;
  - a fake Turnstile token gets 400 `TURNSTILE_FAILED`;
  - `st_oauth` is `Secure`;
  - API responses are `no-store` and `nosniff`;
  - startup logs contain no secrets.
- **Client IP** (preview limit temporarily 3):
  - requests from one machine with different forged `X-Forwarded-For` values shared one bucket and got 429 after the limit;
  - a client-sent `CF-Connecting-IP` is rejected by Cloudflare itself (403, error 1000);
  - a phone on a mobile network, a different client, still got 400 while this machine was limited, so clients do not share a bucket.

## Addendum: staging worker (2026-10-03, Phase 4 PR B)

- **Worker** is a Render background worker (`type: worker`, `stepler-staging-worker`, Frankfurt, `0.5c-512mb` like the API, branch `stage`, `autoDeployTrigger: checksPass`). It runs `apps/api/worker.Dockerfile` (`node dist/worker/main.js`), has no port and no public or private network endpoint, and talks only to PostgreSQL and R2 (ADR 0009).
- **Env:** `DATABASE_URL` from the Blueprint; `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` are `sync: false` and entered by the owner (the same staging bucket as the API; Render cannot copy values between services). No SMTP, Turnstile or `APP_SECRET`.
- **Migrations:** the worker has the same `preDeployCommand` as the API. Prisma's advisory lock makes concurrent runs safe, and whichever service deploys first finds the schema it needs. pg-boss keeps its own `pgboss` schema, which it installs and migrates itself.
- **Connections:** about 23 at peak (API Prisma 10 + pg-boss 2, worker Prisma 5 + pg-boss 5, one migration). The `0.1c-256mb` database's connection limit is not verified; check it in the Render dashboard.
- **Cost:** background workers have no free tier; one more `0.5c-512mb` instance (owner confirms, W1). Media processing (PR D) may need a larger plan (W4).

## Addendum: production Blueprint (2026-10-20, prepared, not created)

- **Separate Blueprint** `render.production.yaml` (Render allows a custom Blueprint path and several Blueprints per repository): `stepler-db`, `stepler-api`, `stepler-worker`, `stepler-web`, Frankfurt, branch `main`, manual deploys (`pnpm deploy:production`, the same ordered script as staging). This settles the open "separate Blueprint or environment" point above.
- **Sizes from the staging load test** (150 guests × 4 photos on one link, 2026-10-19/20). The `0.1c-256mb` database hit 100 % CPU and 52 of 600 uploads failed. With `0.5c-1g` and a `1c-2g` worker at `WORKER_MEDIA_CONCURRENCY=3`, all 600 succeeded. Database CPU peaked at 28 % (22 connections), the worker at 55 % and 370 MB. Production therefore uses the database at `0.5c-1g` with 5 GB, the worker at `1c-2g` with 3 media jobs, and the API and the web at `0.5c-512mb` (the API peaked at 0.18 CPU). That is about $60 a month before bandwidth. Not measured: 48 MP HEIC at 3 at once.
- **Production-only settings:** `SEARCH_INDEXING=on`, no `LEGAL_ALLOW_DRAFT`, and `BILLING_FISCAL_MODE`/`BILLING_FISCAL_WAIVED` prompted (live keys refuse to start without one). `BILLING_RETENTION_DELETE_ENABLED=false` until the legal texts are confirmed.
- **Backups:** Render point-in-time recovery, 3 days on the Hobby workspace (7 on Pro), restoring into a new database; manual exports are kept 7 days. R2 originals have no second copy (open, the owner decides; see docs/deployment/production.md §6).
- Runbook: docs/deployment/production.md. Staging keeps its cheap plans until launch (owner, 2026-10-20).
